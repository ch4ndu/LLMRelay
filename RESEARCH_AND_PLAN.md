## Selected architecture: LLMRelay owns the application

**Approved:** LLMRelay owns its task ledger, state transitions, scheduler, workspace management, execution tracking, and human review. It runs Codex and Claude Code through installed CLIs and implements an initial app-owned workflow based on the user's TRIP rules. LLMRelay owns role sequencing and CLI/PTY sessions; the installed TRIP launcher and cmux are not runtime owners. No Jinn daemon, database, plugin host, adapter, or fork is required.

**Recommended implementation shape:** one local application service with internal modules, one transactional database, and filesystem-backed transcripts/artifacts. The browser and future CLI/MCP interface call the same application operations. Managed CLI/PTY processes belong to the LLMRelay execution supervisor. They are not separate task-management services. Durable task state remains authoritative; transcripts and artifacts are written as needed. Selected implementation: Rust engine, React/TypeScript dashboard and SQLite state, packaged as a foreground command-line executable with bundled dashboard assets.

| Module / layer | Responsibility and boundary |
| --- | --- |
| Web UI | Projects, Tasks, session tree, split terminal panes, execution controls, review inbox, History & archive; never owns dispatch or completion truth |
| Application operations | Validate commands, enforce actor authority and task versions, transact state and event records, serve all clients consistently |
| Persistence | Task records, audit events, transcripts/artifacts, replay cursors, and restore checkpoints; write as needed and report storage failures accurately |
| Task scheduler | Select eligible tasks, enforce repository/global/provider capacity and priority, persist claims, and reconcile before retry; delegates within-task transitions to the workflow engine |
| Workspace manager | Resolve repository identity/base refs, create attempt worktrees, record revisions, retain recoverable changes |
| Execution supervisor | Own CLI/PTY lifecycles, input leases, manager/descendant identities, session-ID bindings, output capture, restore reconciliation, and shutdown independently of viewers |
| Workflow engine | Enforce the initial TRIP-derived role sequence, review/approval gates, counters, control boundaries, and configuration revisions; it is the sole owner of role dispatch |
| Provider CLI adapters | Launch installed CLIs with explicit cwd/model/effort/permissions, capture native session identity through supported mechanisms, and implement verified terminal input/interrupt/resume; no provider API or SDK client |
| Review operations | Bind feedback and acceptance to exact result revisions; queue rework atomically; completion never implies merge |

Agent-facing task tools cannot invoke human-only acceptance or manufacture approvals. Viewer streams cannot update execution ownership.

### Durable execution and state invariants

- Save the attempt's starting brief, plan, routing, policy, and base-revision references. Active configuration changes append revisions rather than rewriting launch history; each invocation records its immutable effective configuration. Active scope changes use guidance or explicit replan.
- In one transaction, claim an eligible issue, reserve capacity, create its attempt, and record dispatch intent. The supervisor launches against that identity. A crash between transaction and process launch requires reconciliation; an expired lease alone is not proof that a writer stopped.
- Store process start identity and provider/workflow session identities, not only a PID. Until an unknown writer is resolved, keep its repository slot unavailable while unrelated repositories can progress.
- State changes and their audit events commit together. Use command idempotency keys, expected task/review versions, and per-stream epoch/sequence identities for retries and reconnects.
- Keep transcript I/O bounded and separate from dispatch/state transactions. Capture gaps and storage failures are explicit. A viewer error cannot accept, cancel, or retry a task.
- Rework atomically binds the review decision to the next attempt lineage and preserves the reviewed code. A checkpoint continuation is visible as such, never misreported as native provider-session resumption.

### Local workflow command contract

Provide the manager and roles with an LLMRelay task CLI connected only to the local service. This is the initial machine channel; a future MCP wrapper can invoke the same operations. Use structured input on stdin, recorded output, and operation IDs. No AI-provider API or SDK is involved. These operation names describe the proposed contract, not commands available today:

| Operation | Caller and service behavior |
| --- | --- |
| Read context / pending controls | Return the current task, attempt, role generation, configuration revision, plan/evidence references, and pending user actions scoped to that caller |
| Request next role | The current manager proposes work and its handoff; the engine validates phase, approvals, counters, ownership/capacity, and control state before reserving and launching the role |
| Report role result | A role submits structured outcome and candidate/evidence references. The service correlates them with the supervisor's process outcome; this does not bypass manager assessment or accept the task |
| Request input / plan approval | Persist a typed request tied to the attempt, plan revision, and blocked phase; project it into Needs input and the attention inbox |
| Submit review handoff | The manager supplies acceptance-criteria evidence, review dispositions, validation references, and exact result revision. The engine checks required gates before moving to Awaiting review |
| Acknowledge guidance / checkpoint | Record the matching control ID, role generation, and saved handoff. The engine confirms process quiescence separately before reporting Pause or Switch complete |

The service issues per-launch credentials scoped to the permitted operations and task/role identity. Manager ownership has a generation token; stale managers and old role processes cannot dispatch or submit authoritative updates after replacement. Identity fields supplied in a prompt are not authentication. Save human approval, feedback, and configuration changes through human-authorized application operations; the agent task CLI cannot accept work or manufacture human approval. Reject duplicate or stale operations without duplicating launches. Validate artifact paths and candidate identity before consuming results.

Process lifecycle comes from the supervisor; declared questions and handoffs come from the local task command; human decisions come from the UI. A zero exit code, terminal phrase, ledger entry, or unvalidated agent claim alone cannot finish a task. If a role never reports the required result, show an incomplete/blocked outcome rather than infer success.

The engine checks its persisted control state before every role launch. Pause-after-role prevents the next dispatch after the current role settles; Run-next-role grants exactly one permitted dispatch and then holds again. Retry creates a new role generation within the same context and consumes the applicable budget. Pause now and cancellation stop new dispatch immediately and request interruption/quiescence of active processes; they remain pending until confirmed. These controls are enforced by the service even if an agent manager requests more work. Manager prose is not the enforcement mechanism.

### Mid-task configuration changes

**Selected policy:** use the new values at the next invocation by default, with an explicit Checkpoint and switch action when the user wants an earlier replacement. The UI shows Running with, Requested change, and Takes effect at per affected role. Saving settings is not proof that the current process has switched.

| Situation | Behavior |
| --- | --- |
| Before session start | Edit all five role rows and validate the resolved configuration before launch |
| Role has not started | Its next invocation uses the latest explicitly saved task configuration |
| Role is already active | It keeps its launch configuration. The change remains pending for that role's next invocation; no unrelated role or other task is restarted |
| A retained role is about to receive another turn | Treat delivery under changed settings as a new invocation boundary. Resume with the changed configuration only where the CLI explicitly supports it; otherwise create a replacement with a recorded handoff |
| Checkpoint and switch | Stop affected dispatch, preflight the requested replacement, persist the switch intent, obtain a consistent handoff and process quiescence, then launch under the new configuration. Do not overlap old and replacement writers |
| Manager switch | Stop all new dispatch for that task. Establish an ownership checkpoint including active child identities and pending controls; revoke the old manager token and stop its input/process before granting ownership to the replacement. Existing children may finish into service-owned records while dispatch is held; no second manager can authorize work |
| Unsupported or failed replacement | Show Switch blocked/failed and retain the pending configuration. Keep already-valid work and unrelated tasks running. If the old role has stopped, leave the affected task paused/blocked; returning to the old configuration is explicit, not automatic fallback |

If a clean checkpoint cannot be obtained, show Waiting for checkpoint. Offer an explicit stop-and-recover path with retained work and an incomplete-state marker; do not report a seamless switch or replay uncertain commands. Service restart recovers the persisted switch state, old/new process identities, and current ownership before attempting further launch. Settings edits arriving during a switch create a later revision; an in-flight launch uses its recorded revision and never changes silently.

For a same-provider compatible change, native resume may preserve that role's conversation. For a provider change, start a new native session with a structured handoff: task/criteria, approved plan, configuration/permissions, worktree/revision, performed work, valid evidence, unresolved findings, pending guidance, and current counters. Cross-provider handoff is explicitly labeled; it is not native context transfer. A replacement reviewer starts independently on the frozen candidate and produces its own complete verdict; a partial verdict from an interrupted reviewer cannot stand in for the replacement's review.

A settings edit or checkpoint switch does not erase completed evidence, reset context budgets, or reopen completed roles. Invalidate evidence only when its candidate, scope, policy, or required checks changed. An explicit request for a fresh second opinion is a new review invocation consuming the current context budget. The final gate reviewer remains an evidence-producing role; only the user's acceptance reaches Done.

### Input ownership and workflow integrity

Use one interactive input lease per live CLI session, bound to its process identity, session ID, role generation, and current input state. Multiple browser viewers can observe; they must not send overlapping keystrokes or race manager automation. An expired/replaced lease rejects stale input. After process exit, disable input rather than forwarding queued prose to a replacement shell. The session launches the agent directly where possible and does not silently fall back to a writable shell on exit.

Manager sessions are the normal interaction target. Worker/reviewer panes remain observable; workflow operations are enforced by the engine and reported to the current manager. If manual takeover of a worker is offered, it is an explicit action: pause affected dispatch, quiesce conflicting automation, record the owner, and invalidate affected review evidence before returning coordination to the manager under engine enforcement. It is not enabled by merely focusing a pane. The initial essential granular controls are the engine-enforced operations in the table; unconstrained concurrent shell access is not implied.

For live Send guidance, use supported CLI input/hook behavior and preserve the message/acknowledgment record. If a CLI accepts new input only when idle, keep guidance visibly queued until that point. Interruption is a recorded request; a terminal Ctrl+C or process signal alone does not prove all descendants stopped. A provider cannot be assumed to support pausing at an arbitrary internal model step. Pause-after-role and Run-next-role are service dispatch boundaries enforced by the engine, as defined in the local workflow command contract.

Role provider/model/effort edits use the configuration-revision and switching contract below. Permissions are a separate execution-policy setting: changing a model does not elevate access. CLI control limitations must be visible before starting a role under a configuration that requires them.

## Session restoration with prior context

cmux is a behavioral reference, not a runtime dependency. Its current documentation distinguishes saved layout/scrollback from native agent context: hooks capture a supported agent's session ID, then restoration invokes that agent's resume command. It does not checkpoint arbitrary process memory. This explains how a reopened terminal can continue the earlier conversation. [cmux session restore](https://cmux.com/docs/session-restore).

LLMRelay should implement the same useful separation:

- **Workspace restoration:** reopen project/task/session tabs, splits, sizes, selection, and saved scrollback for all sessions, including ended sessions. Opening history never launches work.
- **Live reattachment:** when the LLMRelay service still owns a running CLI/PTY, reconnect the browser to that same process. No new agent is started.
- **Native context resumption:** when a process ended, resume its exact native session through the installed CLI in the recorded worktree after reconciliation and policy checks. Provider-managed history supplies conversation context; the dashboard transcript is not a substitute.
- **Workflow recovery:** restore the manager's plan revision, completed gates, pending guidance/reviews, role generations, counters, and workspace state. The service reconciles descendants before allowing the manager to continue coordination or dispatching another role.

Persist a session binding when first learned and when it changes: provider/executable version, native session ID, task/attempt/context/role generation, cwd/worktree/base/result references, effective model/effort/permissions, process start identity, last verified workflow checkpoint, desired running/paused state, and supported resume method. Keep secrets in provider-owned authentication storage; restore records contain no copied tokens. A saved session ID alone is insufficient if the native history has been disabled, removed, or cannot be resumed by the selected CLI version.

| Restart case | Required behavior |
| --- | --- |
| Browser reload/close/reopen | Rebuild the workspace and reattach to live service-owned PTYs; replay available recorded output and reconnect to the live stream without relaunch |
| Planned service restart/update | Stop new dispatch, request a recoverable checkpoint/quiescence, complete pending saves, persist restore bindings, stop descendants deliberately, then reconcile and resume eligible previously-running work after restart |
| Service crash/forced termination | Restore the latest durable records; identify surviving descendants first. Reattach only if the supervisor genuinely retained an attachable PTY; otherwise reconcile/stop survivors before any replacement. Never infer safe restart solely from a dead service PID |
| Laptop reboot/power loss | No local process survived. Reopen workspace and resume supported native sessions from available provider history after worktree/policy checks; mark any capture gaps |
| Paused/Needs input/Awaiting review/Done | Restore the view and native-session binding while keeping execution stopped. Restart does not approve a plan, accept a result, or rerun a completed role |
| Missing native history or incompatible CLI | Show Context unavailable or Resume blocked. Offer a separately labeled checkpoint continuation only with explicit user choice; do not silently start a fresh session and call it restored |

Proposed restore policy: restore the entire visual workspace automatically; offer an Auto-resume previously running tasks setting and Resume selected / Resume eligible controls. Saved authorizations and queue policy still apply. Reconcile all recorded processes first, then resume eligible managers and their required role sessions under the workflow engine, within repository/provider/global limits. Do not blindly launch every saved worker/reviewer at once or reset bounded review loops. A previously accepted result remains accepted without waking its agents.

Resuming the native conversation does not guarantee that an interrupted shell command completed or that external side effects can be replayed safely. Reconcile recorded command/check outcomes with workflow evidence before rerunning. A session resumed through a new process retains its task/context lineage but gets a new process/stream identity.

Provider session persistence is a feasibility requirement for each promised interrupted-role restoration. Resume only the same role generation, reviewed candidate, and compatible configuration. A completed reviewer is not relaunched merely to restore its pane. A new review of a different candidate starts a fresh independent session with explicit findings/handoff inputs. Preserve role independence: never substitute the manager's or another reviewer's native conversation. The app adapters must not inherit the global runner's disabled-persistence flag for resumable sessions.

## Persistence and recovery

**Latest user decision:** write to disk whenever needed. There is no scheduled-flush requirement, write-reduction target, or custom delayed-persistence subsystem. Use normal storage and file I/O behavior appropriate to reliable task execution, live transcripts, and session restoration.

Persist task edits, submitted feedback, approvals, execution ownership, native session bindings, workflow checkpoints, and result evidence before reporting the corresponding operation as saved or allowing a dependent action. Keep state transitions and their audit events consistent, and report storage failures accurately. Preserve provider-native session history and required TRIP artifacts for context restoration and review.

Save transcripts and workspace state as needed. Live views must remain responsive, output handling must remain bounded, and a viewer failure must not change task status. The application transcript keeps a fixed recent-output envelope per session: a 10 MiB steady file is amortized-compacted to approximately 6 MiB, retaining only complete recent JSON frames and an explicit eviction gap before capture continues. Atomic replacement can temporarily hold the old 10 MiB file and the approximately 6 MiB replacement, so the documented per-session application-transcript disk envelope is approximately 16 MiB during compaction and 10 MiB otherwise. A stale evicted cursor receives a recoverable gap and the current retained tail. Starting a new native epoch recovers capture even when the legacy application transcript is already full; a superseded epoch writer cannot rotate or overwrite the current generation. This bounded application scrollback does not delete or replace provider-native CLI history used for conversation resumption. Reconnect and crash recovery should replay available recorded output, deduplicate events, and identify capture gaps without inventing missing history. The chosen storage implementation defines durability guarantees; implementation verification must cover interrupted writes and storage failures.

Abrupt termination can prevent a final record; report the last known state and evidence gaps rather than promise that every failure has a known cause.

### Correlation and event contract

Use one shared structured logger and versioned event schema across application modules. Every record includes UTC timestamp, severity, stable event code, component, operation, outcome, message, app build/version, instance/boot identity, and a unique event identity. Record durations with a monotonic clock and stream sequence/epoch where appropriate; wall-clock changes cannot determine execution order alone. Add request/operation/incident ID, project ID, task ID, attempt/context ID, role/invocation/generation, configuration/policy revision, native session reference, and process start identity whenever applicable. Include executable and CLI versions and the capability evidence revision used at launch. Log an allowlisted launch description, not a raw command line that may contain prompts or credentials. ### Verbosity, retention, and failures in logging

Normal operation uses INFO plus WARN/ERROR; it must already include the major lifecycle, dispatch, gate, ownership, and recovery decisions needed to explain a failure. DEBUG adds targeted internal detail. Provide `--log-level debug` for foreground reproduction and a task/component-scoped temporary diagnostic setting in the dashboard. Proposed default for a temporary override: 15 minutes, then return to the previous level. Changes to verbosity are themselves recorded. Debug mode never enables credential or full-prompt capture automatically.

Use rotation and bounded storage rather than unlimited files. Proposed operational-log defaults: rotate at 10 MiB per file, retain up to 14 days, and cap the complete instance operational-log set at 200 MiB, deleting the oldest rotated operational files first. Display the actual oldest retained timestamp and any size-limit truncation; 14 days is not guaranteed under high volume. Scope this cleanup to operational logs only. Task history, required evidence, saved failure summaries, transcript retention, and worktree cleanup are separate contracts; archiving a task is never permission to delete them. A failed attempt retains an authoritative failure summary and evidence references even after older operational logs expire.

Bound record size and output-processing memory. Store large required evidence as artifacts and reference it; mark truncation explicitly. Coalesce repetitive debug/health messages with counts and first/last timestamps. Never intentionally sample away unique errors, human decisions, ownership changes, or recovery outcomes. Application audit decisions continue to commit with state, independently of the log sink.

If the diagnostic sink becomes unavailable or saturated, report a degraded-diagnostics state in the UI and stderr, record dropped-message counts when possible, and avoid recursive logging failures or an unbounded memory queue. Failure of an optional diagnostic sink alone must not fabricate task failure or acceptance. If authoritative state or required evidence cannot be saved, block the dependent transition and report the actual storage failure. On restart, detect a missing clean-shutdown marker and reconcile from durable state; do not invent a crash stack trace or assume the last log line was the cause.

Write records when needed using normal storage behavior. There is no one-minute flush schedule, write-throttling requirement, or custom delayed-persistence layer.

### Redaction and diagnostic export

Keep diagnostics local by default; no hosted telemetry or automatic upload is required. Redact before operational-log persistence and export. Exclude credentials, tokens, authorization headers, cookies, environment dumps, raw prompts, source-file bodies, and arbitrary request/response payloads from operational logs. Use allowlisted configuration fields and command metadata. Sanitize untrusted values so task text, provider output, and newlines/control characters cannot forge log entries. Transcripts follow their separately documented redaction policy and may still contain sensitive project content; secret detection is not guaranteed to be complete.

Export a task/time-scoped bundle containing a manifest, application/CLI versions, sanitized configuration and capability metadata, related operational events, selected task/attempt lifecycle and recovery records, and saved failure summaries. Explain missing or expired logs. Read a consistent application snapshot rather than blindly copying a live database or mixing revisions. Exclude raw databases, provider credentials/native history, repository content, transcripts, and worktree snapshots by default. Allow the user to deliberately include selected transcript/evidence excerpts after reviewing the file list and sensitivity notice. Replace user-home and repository roots with consistent aliases in exports while preserving correlation. Report export errors and partial results honestly; never advertise the bundle as fully secret-free. Saving an export is local and never sends it to another person or service.

## Proposed workflow and automatic board movement

The UI should derive placement from durable task state, execution phase, and attention state. A browser refresh, reconnect, or duplicate event must not change what the task means. Agent text is evidence to validate, not an unrestricted instruction to move a card or accept a result.

| --- | --- | --- |
| User drafts an issue | Backlog | Saved issue |
| User makes a sufficiently specified issue eligible | Ready | Acceptance criteria, repository/agent routing, and execution policy |
| Scheduler claims an issue | Ready, with Starting indicator | Durable claim and attempt ID |
| Runner confirms work started | In progress | Matching attempt/session event |
| Implementation enters required checks | Validation | Recorded phase and check execution |
| Agent asks a question or needs authorization | Needs input view/lane | Explicit request, preserving the prior phase |

## Proposed priority scheduling rules

1. Select only unarchived Ready issues with an allowed agent, satisfied dependencies, no active claim, and available project/global capacity. Completed and archived records are never eligible simply because their visibility changes.
2. Order by explicit priority, then manual order within that priority, then creation time and a stable ID. Record why an issue was selected.
3. Do not interrupt existing work when a higher-priority issue arrives. Use the new order for the next available slot.
4. Persist the claim and attempt identity before starting the agent. Reconcile a crash between recording and launching before issuing a replacement run.
5. V1 runs tasks concurrently across repositories, with one active coding task per physical repository. Separate worktrees do not enable same-repository concurrent task execution in v1. One task's role sequence is enforced by the workflow engine; additional same-repository writer lanes are outside this version.
6. Keep separate branches/worktrees for coding attempts. Worktree isolation prevents working-directory collisions but is not a permission sandbox.
7. An issue waiting for review may free execution capacity, while its dependents remain ineligible until accepted prerequisite changes are available in their execution base.
8. Retry transient failures with limits and backoff. Authentication problems, unresolved questions, and exhausted budgets remain visible; they must not cause an endless restart loop.
9. Preserve the effective role configuration for each launch. A user-requested configuration revision is an explicit change, not fallback. Missing or unsupported selections block that launch; no automatic provider/model substitution is enabled in v1.

Budget controls should use time limits, retry limits, concurrency, and provider-reported usage when available. Do not present approximate dollar estimates as hard spending enforcement.

## Completed-task ledger, visibility, and archive

Keep every completed task as the same durable task record with its original ID, project, description, acceptance criteria, completion/acceptance time, attempts, review feedback, validation evidence, activity history, and recorded branch/revision references. History is a view over those records, not a second collection copied at completion. Archiving changes visibility and organization; it does not delete or rewrite the task or detach it from other tasks' dependencies.

Proposed defaults for the clarified requirement:

- **Tasks:** Show unarchived tasks. Hide completed is enabled by default, keeping the working view focused. Turning it off shows unarchived completed tasks in Done. Completing a task shows a clear confirmation with a route to its history, so it does not appear to have been lost.
- **History & archive:** Show all completed tasks, whether archived or not, with a simple All completed / Archived filter. Search by task ID/title and filter by project or completion date. Open any record to inspect its evidence and attempts. Pagination keeps a large ledger from being loaded into the browser at once.
- **Archive:** Offered for completed tasks from their detail/history row or selected completed tasks. Record `archivedAt` and actor metadata while retaining the completed status. An archived task is excluded from active task queries regardless of Hide completed. Reject an archive action when an active attempt exists; do not hide ongoing work.
- **Restore:** Clear archive metadata, preserve completion status, and add a restoration event. With Hide completed enabled, the restored task remains in History & archive; turning the filter off reveals it in Tasks. Restore never launches an agent.
- **Reopen:** A separate explicit operation if later needed. It retains the earlier accepted attempt and moves the task into Backlog; it does not implicitly make it Ready or rewrite the completed result. Do not overload Restore with reopening.

Distinguish a per-user/per-project view preference from the task's archived flag. A visibility filter does not mutate tasks. Archiving and restoration should be idempotent, use the task's current version, and report save failures without falsely hiding/restoring a task. No archive action implicitly merges a branch, cleans up a worktree, or purges transcripts. Any future log-retention or workspace-cleanup policy must be explicit and must preserve the completed-task ledger and recorded evidence references; archive is not a cleanup trigger.

Store completion status and archive metadata separately in the LLMRelay ledger. A task remains retrievable by stable ID after archiving, and its completed prerequisite evidence continues to satisfy existing dependency checks where the accepted changes are available.

## Request changes: feedback and rework contract

The first board concept only moved an issue back to Ready when Request changes was clicked. That was a missing interaction, identified by the user. The updated concept opens a form first.

1. **Open form:** Keep the issue Awaiting review and display the exact attempt and result revision being reviewed. Provide a required free-text change description. Support optional references to acceptance criteria, an external review URL, or a plain file/line reference. An embedded diff-comment editor is excluded from the first version.
2. **Draft or cancel:** Typing does not change issue state. Cancel closes the form without submitting feedback, launching an agent, or invalidating the existing review. Preserve drafts per review target in the eventual product; the sample only holds local in-memory form values.
3. **Submit:** Reject blank feedback. Save a review decision, its author/time, target revision, requested changes, and attached comments. Guard against a stale revision and duplicate submission. If saving fails, retain the text and keep the existing state; do not claim rework was queued.
4. **Queue rework:** Atomically associate the saved review with rework for the same issue. Keep the previous result and evidence immutable. The next attempt receives the original issue/acceptance criteria, the reviewed plan and result, and the complete requested changes with attachments/comments. Create a new linked attempt and workflow context based on the exact reviewed result, preserving its changes. A reviewed result may contain uncommitted work, so the workspace layer must capture a recoverable result snapshot and verify the rework base; it cannot assume HEAD alone contains the reviewed code or create a commit implicitly. The new attempt gets a separate workspace/branch populated from that result snapshot. Never restart from an unrelated clean base.
5. **Honor dispatch policy:** The issue returns to Ready with a Changes requested indication until its repository slot and workflow gates permit execution. Do not interrupt another issue automatically. Default rework preserves the issue's priority and follows its queue policy. A correction materially changing the architecture/scope triggers the selected TRIP plan-review/approval rules instead of bypassing them.
6. **Return for review:** The agent addresses each requested change, validates the affected behavior, and reports addressed, unresolved, or disputed feedback. Preserve earlier findings rather than erasing them. After the relevant independent reviews and manager gate, create a new handoff tied to the new result revision. User acceptance remains required; none of these actions implicitly merges a branch.

### Review budget and approval lineage for rework

**Selected:** a submitted human Request changes after Awaiting review creates a new linked context with a fresh bounded plan/code/final-review budget. Preserve the previous context's counters, findings, approvals, result snapshot, and feedback immutably; this is a new user-requested attempt, not a reset of the old context. Automatic repair, process restart, role replacement, and mid-task settings changes remain in the current context and cannot refresh its budget. Duplicate submission creates no second context.

Carry forward a prior plan approval only through an explicit choice in the Request changes form, storing its recorded reference after checking that plan revision, acceptance criteria, authorized scope, and execution policy still apply. A material scope/architecture change requires a new plan review and human approval before affected implementation. The new context must review and verify its new result; old code/final-review evidence is history, not proof for changed code. The manager reports how each requested change was addressed and the app enforces the required gates before returning to human review. Rework inherits task priority and latest task-specific role configuration without pulling in changed global defaults.

Example feedback: “Keep focus state in the existing coordinator. Remove the new global store and verify focus after dismissing search.” The reviewer can include a file/line reference from their external review tool. The next attempt must receive this exact feedback; a generic “please fix the task” prompt would lose the reason for rework.

Request changes concerns a completed result awaiting review. Send guidance concerns work currently in progress. Both record user intent and acknowledgment, but have different state transitions and recovery behavior. Stable role/context/attempt mapping is required for both.
